## 3. Architecture and data flow

`Raw files → Bronze (PostgreSQL + MinIO Parquet) → Silver (cleaned PostgreSQL + MinIO Parquet) → Gold (dimensional PostgreSQL + published MinIO Parquet) → mart SQL views → reporting.py → timestamped CSV exports → Power BI (planned)`.

- **Bronze:** preserves ingested source records, source identity, batches, and ingestion metadata.
- **Silver:** validates and standardizes formats and types, deduplicates across timesheet inputs, manages null/sentinel values, and publishes cleaned relational and Parquet outputs.
- **Gold:** maintains analytical dimensions/fact data. `dim_employee` includes sparse source HR profiles plus referenced employee identities; `dim_date` supplies calendar attributes; `fact_timesheet` represents timesheet events.
- **Phase 6 marts:** query Gold using approved/provisional classification rules and model KPIs, without modifying source Gold records.
- **Reporting:** reads a consistent PostgreSQL read-only snapshot and writes reproducible, checksum-verified CSV extracts.

The API should not perform CRUD directly on the published Gold dimension. An appropriate mutable application/transactional model will be designed in the API phase. Power BI can consume stable reporting exports or PostgreSQL marts; its interactive dashboard is not required to be part of ETL task execution. Future orchestration will call Bronze, Silver, Gold, analytics, reports, and verification in dependency order.

## 6. Nine mandatory KPIs: definitions and SQL locations

| # | KPI | Reporting SQL view | Definition and caveat |
|---|---|---|---|
| 1 | Active Headcount Over Time | `mart.workforce_monthly` (09) | HR-profiled staff active at monthly reporting cutoff: hire on/before cutoff; termination after cutoff or null |
| 2 | Turnover Trend | `mart.workforce_monthly` (09) | Monthly terminations divided by mean opening/closing headcount, multiplied by 100 |
| 3 | Average Tenure by Department | `mart.department_tenure` (10) | Mean calendar-day duration from hire to termination or cutoff, grouped by recorded profile department |
| 4 | Average Working Hours per Employee | `mart.kpi_employee_working_hours` (07) | Eligible-classified work hours divided by workdays/weeks with eligible work; source in 06 |
| 5 | Late Arrival Frequency | `mart.employee_attendance_daily` (05) | Actual punch-in strictly more than five minutes after scheduled start on attendance-eligible events |
| 6 | Early Departure Count | `mart.employee_attendance_daily` (05) | Actual punch-out strictly more than five minutes before scheduled end on attendance-eligible events |
| 7 | Total Overtime Count | `mart.employee_overtime_daily` (08) | Count of eligible shifts with actual elapsed duration exceeding scheduled duration by **more than five minutes**; proxy, not payroll overtime |
| 8 | Rolling Average Working Hours | `mart.kpi_rolling_working_hours` (07), daily basis in (06) | Seven-calendar-day lookback, averaging recorded eligible workday observations; not zero-filled days |
| 9 | Early Attrition Rate | `mart.kpi_early_attrition` (10) | Terminated before completing 90 calendar days / hires observed for at least 90 days, ×100 |

**Metric conventions:** The five-minute grace threshold is strict (`> 5`, not `>= 5`); a six-minute delay qualifies, five minutes does not. Zero denominators use `NULLIF` to avoid misleading divide-by-zero values. Tenure uses days and approximate years (`days / 365.25`). The early-attrition cohort excludes hires whose full 90-day observation window has not elapsed. Monthly complete-period flag is false for April and October 2025, since Gold covers only 2025-04-18 to 2025-10-17.

## 8. Pay-code policy and data quality

Pay codes have composite strings separated by `|`; the pipeline registers raw values and decomposes them into components before creating per-fact classifications. Explicit provisional rules recognized 10 components: three `regular_work`, one `overtime_related`, two `paid_leave`, two `unpaid_leave`, one `administrative`, and one `orientation_training`. **236 of 246 components remain unclassified.** Therefore, classification coverage is intentionally conservative; unknown components are not silently treated as worked time.

| Reconciliation | Observed count |
|---|---:|
| Gold timesheet records | 381,732 |
| Eligible work-status records | 273,918 |
| Excluded records | 29,397 |
| Unresolved records | 78,417 |
| Attendance-eligible events | 132,724 |
| Late arrivals | 16,386 |
| Early departures | 36,692 |
| Shift-overrun events | 41,668 |
| Total proxy overtime hours | 15,482.2224 |
| Classified worked hours | 2,531,884.61 |
| Total recorded hours | 3,576,290.99 |

These are **dataset-specific observed outputs**, not certified payroll truth. Unclassified/ambiguous codes require future business-owner mapping before completeness claims. Actual elapsed punch time can differ from recorded worked hours (e.g., breaks), so overtime hours are a duration-based *proxy*. An audit found 219 eligible records with punch-duration-versus-recorded-hours differences greater than 15 minutes; no observed overrun exceeded four hours in that audit. Report titles and Power BI labels should retain these caveats.

HR dimension has 10,794 identities but just **50 profiled employees**. Workforce KPIs are **not** company-wide measures of all 10,794 referenced employees. Reporting spans seven months, of which April and October are partial; 2025-10-17 is the reporting cutoff. The early-attrition result was 0 early exits among 50 eligible hires (0.00% under the chosen definition). May and June each show one recorded exit within the monthly reporting window.

## 11. Indexing strategy and measured performance

Pre-optimization audit found **9** PostgreSQL indexes: Gold and mart primary/unique indexes, including employee IDs, dates, timesheet event identity and pay-code registries. SQL 14 added **three** deliberate Gold indexes:

| Index | Keys / predicate | Intended access |
|---|---|---|
| `idx_gold_timesheet_employee_date` | `(employee_key, punch_apply_date_key)` | Employee-specific date-range facts |
| `idx_gold_timesheet_apply_date_employee` | `(punch_apply_date_key, employee_key)` | Date-first filtering and employee joins |
| `idx_gold_employee_profile_hire_term` | `(hire_date, term_date)` where source profile and hire date are present | Profiled workforce date queries |

Thus there are **12 indexes** after migration. Recent cumulative usage reads: employee/date 0 scans, date/employee 542 scans, profile/hire 47 scans; these figures do not prove causation for a particular query. `CREATE INDEX IF NOT EXISTS` makes repeat migration safe, but it does not prove an existing index has the intended definition; schema review remains useful. Foreign-key referencing columns are not automatically indexed by PostgreSQL.

**Query benchmark (PostgreSQL `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`, milliseconds):**

| Query | Before indexes | After indexes |
|---|---:|---:|
| Monthly workload | 2,479.063 | 2,629.464 |
| Department workload | 1,643.470 | 1,794.943 |
| Attendance compliance | 1,151.788 | 1,251.169 |
| Department overtime | 1,230.247 | 1,263.053 |
| Workforce monthly | 3.961 | 0.479 |
| Employee working hours | 5,444.155 | 4,959.988 |

**Interpretation:** no consistent speedup across full-table timesheet aggregations; changes may reflect cache/system conditions, query plans, and the volume of classification work. Do **not** claim indexes made analytics uniformly faster. The chosen indexes additionally support future selective API queries. If Power BI refresh performance becomes unacceptable, inspect full query plans, evaluate materializing expensive aggregates, and benchmark under representative repeated workloads before further changes.

## 12. Setup and execution guide

**Prerequisites:** Docker Desktop/services running (PostgreSQL and MinIO), project Python virtual environment activated, dependencies installed from `requirements.txt`, and environment configuration (e.g. `DATABASE_URL`) supplied through the project's existing `.env` conventions. Do not commit credentials. This phase assumes previously completed Bronze/Silver/Gold pipelines and a **published** Gold snapshot.

From PowerShell at `D:\ASE-ETL`:

```powershell
# Make sure the warehouse publication is current before analytics.
python -m src.analytics.pipeline

# Validate all calculation and integration tests.
python -m unittest discover -s tests -p "test_analytics_*.py" -v

# Optional: inspect indexes and profiling results.
python -m tests.audit_analytics_indexes
python -m tests.check_index_usage
python -m tests.profile_analytics_queries

# Export reporting-ready CSV datasets.
python -m src.analytics.reporting

# Verify the latest generated report batch.
python -m tests.verify_analytics_reports
```

**Runtime behavior:** `pipeline.py` handles SQL view definitions, embedded validations, and index creation; it does **not** automatically run the standalone unit tests, query benchmark, CSV exporter, or CSV integrity checker. `reporting.py` is a separate command. These commands will be connected by an orchestrator in a later project phase. The report exporter verifies Gold publication status, fingerprint and registered row counts; it does not yet independently verify the latest active Silver-to-Gold lineage fingerprint.

**Failure behavior:** SQL errors abort the transactional analytics deployment; external CSV exports use a staging folder that is cleaned on failure. Fix source SQL and rerun. For performance debugging use `EXPLAIN ANALYZE` and the index audit; do not automatically create indexes on every column.

## 13. Engineering choices and tradeoffs

1. **Views instead of copying mart tables:** maintain a single Gold warehouse source and avoid duplicated persistent datasets; cost is on-demand recomputation.
2. **Explicit pay-code classification:** conservative unknown handling avoids falsely attributing leave/admin time as ordinary work; cost is incomplete current KPI coverage.
3. **Five-minute attendance grace and 90-day attrition cohort:** reproducible business rules; they must remain visible to stakeholders and may need approval.
4. **Shift overrun vs payroll overtime:** schedules/punches are available, while payroll/overtime authorization and unpaid-break context are not adequately established.
5. **Separate reporting exporter:** reusable CLI for operational scheduling and Power BI consumption, but not yet a full job scheduler.
6. **Repeatable SQL and transaction boundaries:** permit controlled reruns and avoid partial deployment.
7. **Measured indexing:** emphasize PK/unique protection and selective access, backed by observed index usage and query timing, rather than promising universal performance gains.
